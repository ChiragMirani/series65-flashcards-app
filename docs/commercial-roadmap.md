# Smallest safe commercial sequence

These capabilities are **not implemented**. `lib/ports.ts` contains TypeScript contracts, not functioning integrations. Preserve the deterministic engine and `StudyRepository` boundary.

1. **Clear the content release block.** Have a qualified reviewer validate each rule's authority, effective date, exceptions, source provenance, and independent wording. Store approvals against exact content hashes with reviewer identity and date. Keep draft and reviewed-but-unverified cards out of paid release artifacts. Commission human review of wording similarity; automated matching cannot establish rights.
2. **Publish an audited free sample.** Select a small verified deck by stable IDs. Build readable topic pages from human-approved summaries with source citations, answer-first explanations, and review dates. Do not expose private notes. Verify accessibility, offline updating, backup recovery, and browser support on real devices.
3. **Add accounts and cloud persistence.** Implement AuthPort using a supported provider such as Supabase Auth. Use PostgreSQL tables for accounts, content versions, per-card progress, events, and entitlements. Enforce row-level policies and server-side authorization. Import existing local progress only after explicit account association. Use idempotent event IDs, server revisions, and a documented merge/conflict policy rather than silent last-writer-wins replacement.
4. **Define 12-month access precisely.** Choose calendar-month semantics: twelve months from entitlement activation, with a documented end-of-month rule, UTC timestamps, renewal, refunds, chargebacks, and cancellation policy. Server time and server records govern access. Display the expiration date. Never trust browser clocks, client flags, or checkout return URLs as proof of payment.
5. **Add Stripe Checkout and webhook entitlements.** Keep price IDs and secrets server-side. Verify webhook signatures, persist unique event IDs, tolerate retries/out-of-order events, and derive entitlement transitions from verified payments/refunds/disputes. Begin in Stripe test mode. Test failed checkout, duplicate delivery, partial refund, account mismatch, revoked access, and recovery before taking payment.
6. **Add coupons.** Use provider-side coupon/promotion-code controls, eligibility, redemption limits, and audit logs. Avoid client-side price arithmetic as authorization.
7. **Add sync and offline entitlements together.** A downloaded static deck is readable offline and cannot be reliably revoked. Decide the paid offline-license policy before selling access. Serve only authorized content, issue short-lived signed grants if appropriate, and document unavoidable offline limits; encryption with a browser-delivered key does not make a public bundle secure.
8. **Author four full-length original practice exams.** Follow current official category specifications and the design blueprint. Use separate question and explanation entities linked to stable rule IDs. Have humans verify all keys, distractors, calculations, provenance, and psychometric limitations. Keep scoring and answer delivery server-authoritative where product integrity requires it.
9. **Feed missed concepts to a repair deck.** Map each original question to rule IDs. Record knew/narrowed/guessed confidence separately from correctness. Wrong answers and correct guesses can create changed-fact repair tasks. Do not automatically mark a concept mastered after immediate repetition.

After human release approval, use `docs/aeo.md` to configure the canonical domain, indexing, sitemap submission, and measurement. No payment, account, coupon, cloud, or examination capability should be described as working before its implementation and verification.
